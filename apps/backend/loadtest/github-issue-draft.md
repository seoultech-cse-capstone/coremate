# [perf] 백엔드 읽기 API 부하/스트레스 테스트로 한계점 측정

## 배경 / 목적
우리 앱(Spring Boot 4 + MySQL 8 + Redis 7.2)이 **동시 사용자 몇 명까지 정상 처리하고, 어디서
무너지는지(한계점)** 를 정량적으로 파악한다. 배포·시연 전 서버 체력의 기준선을 확보하고,
가장 먼저 터지는 병목을 찾아 개선 우선순위를 정하는 것이 목표.

## 범위
- ✅ **대상**: 일반 읽기 API (출석·콘텐츠·알림·진행률 조회 등, Spring Boot → MySQL/Redis)
- ❌ **제외**: AI 연동 API(`/api/v1/weakness/reports`, LLM 병목이라 별도 이슈), 이메일/외부 연동
- 환경: 로컬 Docker Compose 스택 (`infra/docker-compose.local.yml`)
- 도구: **k6** (`apps/backend/loadtest/`)

## 방법
1. 스모크(VU 1) → 시나리오·계정·토큰 정상 확인
2. 부하(VU 50 유지) → 기준선 측정: 에러율 <1%, p95 확인
3. 스트레스(VU 단계적 증가) → RPS가 정체되고 응답시간/에러율이 급증하는 **무릎 지점** 탐색
4. 부하 중 `docker stats` / 백엔드 로그로 자원(CPU·메모리·커넥션 풀) 병목 관찰

## 측정 지표
- 처리량(RPS), 응답시간 **p95/p99**, 에러율(`http_req_failed`)
- 자원: 백엔드/MySQL 컨테이너 CPU·메모리, HikariCP 커넥션 대기

## 가설 (검증할 병목)
- [ ] **HikariCP 풀 크기 기본 10** 이 1순위 병목이다 → 20~30으로 올려 전후 비교
- [ ] JPA N+1 / 인덱스 미비 쿼리
- [ ] JVM 힙 / 컨테이너 메모리 제한
