# DB 마이그레이션 (Flyway)

이 폴더가 DB 스키마와 정책 데이터의 **정본**이다. 백엔드가 뜰 때 Flyway 가 아직 적용하지 않은 파일을 실행하고,
무엇을 언제 적용했는지 `flyway_schema_history` 테이블에 남긴다. 그다음 Hibernate 가 엔티티와 테이블이 맞는지
검사한다(`ddl-auto: validate`). 테이블·컬럼이 없거나 타입이 다르면 백엔드가 뜨지 않는다.

`scripts/db/*.sql`(약점분석 손검증용 더미·일회성 백필)은 마이그레이션이 아니다.

## 파일 종류

| 이름 | 용도 | 실행 |
| --- | --- | --- |
| `V{번호}__{설명}.sql` | 스키마 변경, 일회성 데이터 보정 | **한 번만.** 번호 순서대로 |
| `R__{번호}_{이름}.sql` | 정책·마스터 데이터(보상 정책·상품·아이템) | **파일 내용이 바뀔 때마다** 통째로 다시. V 가 다 끝난 뒤 이름순으로 |

`V1__baseline.sql` 은 Flyway 도입 시점(2026-09-30)의 스키마 전체다. 이미 테이블이 있던 DB(운영·기존 로컬)에서는
실행하지 않고 "적용됨"으로만 기록한다(`spring.flyway.baseline-on-migrate`).

## 스키마를 바꿀 때

1. 엔티티를 고친다.
2. 같은 PR 에 `V{다음 번호}__{설명}.sql` 을 추가한다. 이 폴더의 `V2`(인덱스 추가)·`V3`(기본값 추가)가 실제 예다.
3. 로컬 백엔드를 띄워 확인한다. 마이그레이션이 실패하거나 엔티티와 테이블이 안 맞으면 기동이 멈춘다.

### 지켜야 할 것

- **머지된 V 파일은 고치지 않는다.** 체크섬이 달라져 그 파일이 적용된 모든 DB 에서 백엔드가 뜨지 않는다.
  고칠 게 있으면 새 V 파일을 만든다.
- **번호가 겹치면 기동이 막힌다.** 병렬 PR 끼리 같은 번호를 쓸 수 있으니, 머지 직전에 dev 의 마지막 번호를
  확인하고 겹치면 올린다.
- **enum 상수를 추가하면 `MODIFY COLUMN` 을 같이 쓴다.** `@Enumerated(STRING)` 컬럼 대부분(40개)이 MySQL native
  `enum(...)` 이라 DB 쪽 목록도 바꿔야 한다. 예전에는 `ddl-auto: update` 가 기동할 때마다 이 40개를 전부 다시 써서
  맞춰 줬지만, 이제는 아무도 맞춰 주지 않는다. 빠뜨리면 기동은 되고, 그 값을 저장할 때 `Data truncated` 로 터진다
  (validate 는 enum 목록을 비교하지 않는다). 지금 정의는 `SHOW CREATE TABLE` 로 보고, 기존 값 전부와 NULL 여부를
  그대로 옮긴 뒤 **새 값은 끝에 붙인다.** 중간에 끼우면 MySQL 이 테이블을 통째로 다시 쓴다.
  ```sql
  ALTER TABLE currency_logs
      MODIFY COLUMN reason ENUM('ADMIN_GRANT', /* …기존 값 전부… */ 'NEW_REASON') NOT NULL;
  ```
- **validate 가 못 잡는 것이 있다.** 인덱스·UNIQUE·FK·기본값·CHECK·enum 값 목록. 엔티티의 `@Index`·
  `@UniqueConstraint` 는 이제 DB 에 아무것도 만들지 않는다 — 필요하면 마이그레이션에 직접 쓴다.
- **직전 버전 코드와 같이 돌아도 되게 쓴다.** 배포 중에는 옛 버전이 새 스키마에서 잠깐 돌 수 있고, 배포가
  실패하면 앱만 이전 버전으로 돌아가고 DB 는 그대로다(Flyway 무료판에는 되돌리기가 없다).
  - 컬럼 추가는 NULL 허용이나 기본값과 함께 한다.
  - 삭제·이름 변경은 두 번에 나눈다. 먼저 코드에서 안 쓰게 배포하고, 다음 배포에서 DROP 한다.
- **파일 하나에는 되도록 변경 하나.** MySQL DDL 은 문장마다 바로 확정돼서, 중간에 실패하면 반쯤 적용된 채
  이력에 실패가 남고 이후 기동이 전부 막힌다. 복구 방법은 `docs/deploy/aws.md` 의 「데이터베이스」.

## 정책 데이터(R__)를 바꿀 때

파일의 값을 그대로 고친다. 배포되면 바뀐 파일만 다시 실행돼 값이 반영된다.

- **멱등이어야 한다.** 파일 전체가 다시 돌므로 UNIQUE 키 기반 `INSERT ... ON DUPLICATE KEY UPDATE` 로 쓴다.
  UNIQUE 키가 없으면 조용히 새 행이 쌓인다 — `R__03` 은 `avatar_items.item_name` 의 UNIQUE 덕분에 멱등이다.
- **번호가 곧 FK 순서다.** R__ 는 이름순으로 돈다. 참조하는 테이블보다 뒤 번호를 쓴다.
  ```
  03 avatar_items          (FK 없음)
  04 random_boxes          (FK 없음)
  05 shop_products         → item_id → avatar_items,  random_box_id → random_boxes
  06 random_box_items      → random_box_id → random_boxes,  item_id → avatar_items
  ```
- **행을 지우지 않는다.** 끄려면 `is_active = FALSE` 로 바꾼다. 파일에서 행을 지워도 DB 의 행은 남아 계속 쓰인다.
  DB 에서 DELETE 하면 `reward_logs`·`xp_logs` 가 가리키는 지급 근거가 끊긴다.
- **다시 실행될 때 DB 값을 파일 값으로 덮어쓴다.** 관리자 화면에서 정책을 고치는 기능(AR-ADMIN-04)이 생기면,
  그 테이블은 V 파일(바꿀 행만 UPDATE)로 관리를 옮긴다.
- 테스트(H2)에서는 마이그레이션이 돌지 않는다. **고쳤으면 로컬 백엔드를 실제로 띄워 확인한다.**

| 파일 | 담당 | 내용 |
| --- | --- | --- |
| `R__01_reward_policies.sql` | — | 보상 정책 19행 (XP 3 / 코인 4 = 최초 통과 2 + 재응시 2 / 퀴즈·출석 2 / 레벨업 6 / 스타터팩·광고·프리미엄 4) |
| `R__02_paid_products.sql` | — | 분석표 생성 가격 1행, 프리미엄 구독 1행 |
| `R__03_avatar_items.sql` | 용주 | 아바타 아이템 38행 (기본 지급 6 / 하 14 · 중 10 · 상 8) |
| `R__04_random_boxes.sql` | 재훈 | 랜덤박스 1종 (STANDARD) |
| `R__05_shop_products.sql` | 재훈 | 상점 상품 2종 (랜덤박스·닉네임 변경권) |
| `R__06_random_box_items.sql` | 재훈 | 랜덤박스 구성 33행 (아이템 32 + 코인 1, 확률 합 1) |

`R__01` 의 레벨업·스타터팩 행은 아직 코인 부분만 있다. 랜덤박스·특별 아이템 지급은 아이템 마스터(`R__03`)가
확정됐으므로 이제 붙일 수 있다.
